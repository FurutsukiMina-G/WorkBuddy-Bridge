# 0.3.2：长回复流式过滤改为线性耗时

## 问题

原生模式的流式闸门（拦截协议标记、参数对象和只宣告下一步的回复）每收到一小段正文，就把已累积的全部正文重新扫描一遍；JSON 文本协议的最终回复投影也会在每一段重新处理全部已解码内容。两者的耗时都随回复长度平方增长，并且占用 worker 的事件循环。此外，V8 对不断追加的字符串每次读取都会整体拷贝，即使只扫描末尾也同样是平方耗时。

## 修改

- 闸门只扫描“还可能改变判定”的部分：已经结束、判定不会再变的行不再重复扫描；行首 `{` 的首个属性尚未由已结束的行确定时，该行保留在窗口中。窗口只会推进到已经流出的位置，尚未流出的正文始终保留。
- 正文按收到的片段保存，读取从最新片段向前进行，只在需要完整文本时拼接一次，避免 V8 反复拷贝不断增长的字符串。
- 很长的单行：若当前行位于代码围栏内，或行首字符不可能开启行内代码、围栏、JSON 对象或调用信封，则只检查新到字符中的 DSML 标记与末尾被拆开的标记；新字符中一旦出现 DSML，交给完整扫描确认（可能是行内代码示例）。
- JSON 文本协议的最终回复投影只解码尚未消费的尾部；规范开头 `{"action":"final","content":"` 共 29 个非空白字符，收到这么多非空白字符仍不匹配时停止尝试投影，最终决策照常完成。
- 判定规则与 0.3.1 完全相同，只改变扫描方式。

## 耗时（8 字符一段逐段推送，单次运行）

| 场景 | 0.3.1 | 0.3.2 |
|---|---:|---:|
| 原生闸门，2 万字符多行回复 | 265 ms | 14 ms |
| 原生闸门，6 万字符多行回复 | 2,225 ms | 18 ms |
| 原生闸门，12 万字符多行回复 | 9,989 ms | 28 ms |
| 原生闸门，3 万字符单行 | 270 ms | 11 ms |
| 原生闸门，6 万字符单行 | 1,052 ms | 9 ms |
| JSON 投影，12 万字符 | 1,179 ms | 5 ms |

仍按完整扫描处理的只有一种形态：没有换行的超长单行，且行首是反引号、`{`、`<`、`"` 或 DSML 字符；约 2.8 万字符耗时约 0.13 秒。

## 验证

- 119 项本地回归与语法检查全部通过。
- 新增对照测试保留 0.3.1 的完整扫描实现作为基准：3,000 段随机文本（含围栏、行内代码、多行 JSON、各类调用标记、代理对和随机切分）逐片段比对流出内容、拦截状态和已流出长度，结果完全一致；3,000 次扫描结果比对与 2,000 段 JSON 投影（含原始控制字符、填充空白的信封、错误转义、非最终信封）同样一致。随机输入中快速路径 1.7 万次、完整扫描 1.7 万次、窗口推进 4 千次。
- 新增线性耗时测试：20 万字符多行回复与约 9 万字符单行在 1.5 秒内完成（实际约数十毫秒），扫描窗口只剩当前行。
