# 0.3.0：原生宿主函数与预启动运行时

## 使用数据复核

范围：`reports/requests.ndjson` 中 2026-10-21 11:46 至 10-22 00:46（UTC+8）的 113 个请求，其中 95 个带逐次尝试记录；以及经本桥回答的 14 个 DSH 会话（8 个真实任务，6 个验收会话），只读取消息形态与协议标记，不复制任务内容。

| 观察 | 数值 |
|---|---:|
| 首轮被格式拒绝的请求 | 54 / 95（57%） |
| 被拒绝的模型调用 | 62 / 155 |
| 被拒尝试占用的总耗时 | 1,465 / 3,063 秒（48%） |
| 被拒尝试消耗的输入 token | 2.41M / 5.25M（46%） |
| 被拒尝试消耗的输出 token | 151K / 211K（72%） |
| 以错误结束的真实 DSH 任务 | 4 / 8（3 次 invalid_decision，1 次两轮慢纠正后超时） |
| 首个思考事件中位数 | 9.1 秒（p10 7.9 秒） |

- 多个被拒尝试先推理 60–160 秒、输出 1 万–2.8 万 token，最后打印出边界错乱的 DSML。`0.2.3` 重放 32 份保留样本后仍有 13 份无法明确解码：缺少 `<`/`</`、用结束标签开启下一参数、缺少 string 属性、`param` 缩写、在 DSML 内嵌套 arguments JSON；另有不带 JSON 外壳的普通最终回复。
- 运行时自身日志显示，约 9 秒的请求中约 5.5 秒花在模型请求发出之前（进程启动、CLI 初始化、登录刷新、插件/MCP 加载），首 token 约 2 秒。每个请求都重新付出这段启动时间。
- 上下文复用本身有效：续接请求只发送新增消息（例如 203.7K 字符中只发送 1.6K），缓存命中高。剩下的重复注入来自纠正：每次纠正都让模型重新读取整段续接上下文。
- 本批 DSH 回复中没有出现协议文本泄漏或“只宣布下一步就结束”的回复；下面的这两项防护属于预防。

## 原因

DeepSeek 的原生工具调用格式就是 DSML。旧实现向运行时声明 0 个工具（`tools: []`），只在文本里要求模型输出 JSON；模型仍按习惯用 DSML 写调用，但没有对话模板里的格式约束，边界越来越乱。JSON 指令无法稳定压过这个习惯。

## 修改

1. **原生宿主函数（默认）**：DSH 的工具按原 JSON Schema 声明为运行时的进程内 MCP 函数 `mcp__host__<name>`，模型通过原生函数调用产生结构化参数，由上游解析。`PreToolUse` 钩子拒绝并停止，桥从不执行；拒绝文本告诉模型宿主结果会在下一条消息给出。运行时只为它停下的第一个调用发出 assistant 消息，并行调用还共用同一个流索引，所以桥从流事件逐个组装全部调用，再整批校验已声明名称、完整 Schema、tool_choice 和并行限制。交给 DSH 的调用 ID 沿用运行时 ID，下一轮只发送宿主结果，不再回显上一轮调用。最终回复是普通文本，不需要 JSON 外壳；模型若仍把调用写成文本，先用 `0.2.3` 的严格 JSON/DSML 解码器处理，解不出才纠正。
2. **不输出协议与参数**：流式正文在发给 DSH 前经过闸门。代码块之外任何位置的 DSML 标记、行首的调用信封（`<invoke`、`<tool_call`、`{"action":…}` 等），以及首个键是宿主参数名的参数对象，都不会流出；被拆开的标记在排除之前先保留。围栏代码和行内代码中的示例照常作为回答。被输出预算截断的调用从不转发。
3. **不提前结束未完成的任务**：240 字以内、只宣布下一步动作（如“我先读取…”、“Let me check…”）却没有调用宿主函数的回复，先不流出，在同一会话内纠正一次；再次出现时作为回答交付，不让任务报错中断。向用户的提问和已完成的报告不受影响。
4. **预启动下一轮运行时**：返回工具调用后，下一轮的运行时（同一会话 resume、相同选项）在 DSH 执行工具期间启动并完成初始化。只有模型、effort、max_tokens、工具、会话和登录完全一致的下一轮才使用它；120 秒未用、选项变化、会话清理或服务关闭时立即结束；最多同时 4 个；初始化前异常退出时改用冷启动一次；最终回复后不预启动。
5. **原生模式纠正**：同一会话、模型、期限内发送一条带原因的纠正消息（参数校验细节、需要调用、未完成宣告或协议文本），仍受 `WORKBUDDY_DECISION_RETRIES` 限制。
6. `WORKBUDDY_TOOL_MODE=json` 保留 0.2.x 的文本协议，行为不变。
7. 每个请求记录 `toolMode`、`warmStart`、`runtimeReadyMs`；`/metrics` 与 `metrics` CLI 新增 `runtime` 汇总（模式计数、预启动次数、冷/热就绪中位数、未完成纠正次数）；`/health` 显示 toolMode、hostCalls 和预启动统计。

## 验证

- 106 项离线回归与语法检查全部通过。新增覆盖：宿主函数按原 Schema 声明且从不执行；沿用运行时 ID；按真实记录的流形态组装并行调用；参数未完整的流式调用被纠正而不转发；续接只发送宿主结果；普通文本逐段流出；只宣告的回复不流出、纠正一次、第二次交付；文本中的 DSML 被解码且不流出；无法解码的标记被纠正；围栏与行内示例保留；参数对象不流出；Schema 错误的原生纠正；超出预算的调用不转发；内置工具、外部 MCP 服务和未连接的宿主服务均失败关闭；tool_choice none；预启动的使用、丢弃、冷启动回退、过期与关闭。
- 有限次真实 Flash 验收：3 次探针请求（原生调用；带宿主结果续接后精确回答；并行调用），以及 `node scripts/native-smoke.mjs --tools <本机记录的 38 个 DSH 工具>` 的 5 次请求，全部通过，0 次格式纠正，未出现 11128。冷启动请求 5.6–6.8 秒，预启动续接 3.2–3.8 秒；运行时就绪约 2.5 秒对比约 0.7 秒；流式最终回复首段 4.95 秒、结束 5.86 秒。带 38 个工具时每次约 13.7K 输入 token，续接轮其中 13.7K 命中缓存。这些是小上下文样本，不代表长任务的固定时延。
- 未验证：经正式服务 8647 的 DSH 端到端任务（本次没有切换正式服务）、长上下文下原生调用的稳定性、WorkBuddy 以后版本的行为。

## 边界

- 依赖上游接受原生工具（本次已验证）。若运行时不再连接进程内服务，请求以 `native_tools_unavailable` 失败，可设置 `WORKBUDDY_TOOL_MODE=json` 回到文本协议。
- 依赖运行时在被拒调用后以 `Max turns (1) exceeded` 停止，以及 SDK 的 `cleanup()` 结束未使用的预启动进程；SDK 版本固定为 0.3.286，升级时需重新验证。
- 未完成宣告的识别是启发式的，每个请求最多纠正一次。
- 预启动最多额外保留 4 个空闲运行时（每个约 140 MB），每个不超过 120 秒。
- 工具定义改为每次随请求体发送（作为可缓存前缀），不再写入首轮 transcript；总 token 量级相近。
